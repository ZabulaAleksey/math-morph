# Правила тестирования

- Исправление ошибки → регрессионный тест или fixture.
- Не утверждай новый эталонный результат только потому, что реализация его изменила.
- Для изменений parser, загрузки и аутентификации включай повреждённые, граничные случаи и случаи безопасности.
- Проверяй наблюдаемое поведение; избегай хрупких тестов внутренних деталей реализации.
- Тесты конфиденциальности должны доказывать, что чувствительный открытый текст не появляется в базе данных, хранилище или журналах, если архитектура утверждает обратное.
- Поддерживай согласованность метаданных и манифеста fixtures.

## Политика тест-контрактов

- Принятый тест, fixture, golden-снапшот или E2E-сценарий — это контракт поведения. Во время обычной реализации он используется только для верификации.
- Принятый тест и fixture нельзя модифицировать, удалять или пропускать в этом же цикле.
- Любой упавший принятый тест означает дефект в production-коде и фиксируется в нём, а не переписыванием теста.
- Изменения уже принятых тестов выполняются только по прямому запросу владельца или в отдельной задаче изменения требований.
- Новые тесты можно добавлять вместе с новой функциональностью до первичной приёмки, но это не даёт права переписывать принятые контракты.

## Критические E2E-сценарии

- Для проверки продукта должны быть определены приоритетные сценарии:
  1. Загрузка валидного `.xmcd`/`.mcdx` и получение редактируемого DOCX.
  2. Безопасная обработка повреждённого/опасного ввода с локализованной ошибкой без создания артефакта и утечки данных.
  3. Аутентификация/2FA/восстановление и выдача API key.
  4. Прогресс конвертации, перезапуск после обрыва сети и восстановление скачивания.
- Если отсутствует production-ready backend, API или CLI путь для любого сценария, оставляй явную пометку `BLOCKED_BY_BACKEND_<scen>` в `docs/ROADMAP.md` или `docs/AI_STATUS.md`; сценарий не считается закрытым до появления рабочего пути.
